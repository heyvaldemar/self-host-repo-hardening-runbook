## Type B standards — proposed Phase 7 (container hardening)

This phase was newly drafted in `RUNBOOK.proposed.md` after the audit surfaced these gaps. Status against the proposed standard:

| Standard | Status | Per-service detail |
|---|---|---|
| `security_opt: ["no-new-privileges:true"]` on every service | 🔴 MISSING | None of postgres / keycloak / traefik / backups has it |
| `cap_drop: [ALL]` + selective `cap_add` | 🔴 MISSING | None drops capabilities |
| `read_only: true` with explicit tmpfs mounts | 🔴 MISSING | All services use the default writable rootfs |
| Memory limit (`deploy.resources.limits.memory` or `mem_limit`) | 🔴 MISSING | None of the four services has a memory ceiling |
| CPU limit (`deploy.resources.limits.cpus` or `cpus`) | 🔴 MISSING | None of the four services has a CPU ceiling |
| `pids_limit` (optional) | 🔴 MISSING | Not applied (optional standard) |
| Explicit `user:` directive on services | ⚠️ PARTIAL | None of the four services has `user:` set. Postgres and Keycloak upstream images run non-root by default (postgres: `postgres` user, keycloak: `keycloak` user). Traefik upstream runs as root. Relying on upstream defaults works today but is invisible in the compose file and could silently flip if an upstream image rebases. |
| Healthchecks on long-running services | ✅ MET | postgres (`pg_isready`), keycloak (TCP HTTP /health/ready), traefik (`/ping` wget). All three with appropriate `start_period` for warm-up |
| Healthcheck on sidecar | ⚠️ PARTIAL (acceptable) | The `backups` container has no healthcheck. Acceptable per Phase 7 step 7 — sidecar pattern. Would benefit from a comment in the compose file documenting the omission. |
| `restart: unless-stopped` on every service | ✅ MET | All four |

**Phase 7 verdict:** 🔴 not yet applied. Largest remaining gap.

### Why the gap matters

Every service in the stack today inherits the Docker default security context — full Linux capabilities, writable rootfs, no resource ceilings. The blast radius of a successful exploit (e.g. an authenticated Keycloak admin RCE, a Traefik plugin compromise, a Postgres extension bug) is therefore wider than necessary. The Phase 7 settings shrink this individually:

- `no-new-privileges:true` — blocks setuid escalation if a process inside escapes its capability set
- `cap_drop: [ALL]` — neutralises capability-dependent kernel attack surface
- `read_only: true` — turns most filesystem-write-based persistence techniques into hard failures
- Resource limits — converts a runaway service from a host-OOM event into a single-service crashloop

None of these settings are individually exotic. The reason they're missing in this repo is that the runbook hadn't codified them yet — this audit is the trigger for Phase 7 being added.

## Other findings (not directly tied to a phase)

### No semver release tags

```
$ git tag -l | head -10
(empty)
```

**Status:** 🔴 MISSING.
**Severity:** HIGH.
**Why it matters:** the README's "Production checklist" tells users to pin to specific image digests for reproducibility, but the README itself never ships at a stable reference point. Users who clone this repo today have to either pin to a commit SHA (opaque, no release notes) or track `main` HEAD (re-pulls every time). A first semver tag — `v1.0.0` after Phase 7 lands, or now if Phase 7 is deferred — gives consumers a stable artifact and aligns CHANGELOG `[Unreleased]` with a real version anchor.
**Effort:** ~30 minutes (pick a version, write release notes, push the tag, draft the GitHub release page).
**Recommendation:** cut `v1.0.0` after Phase 7. Until then, tag `v0.9.0` to anchor the current `[Unreleased]` set if the maintainer prefers signalling "pre-Phase-7 baseline".

### Off-host backup replication is documented but not first-class

The README's **Backups** section says (line 144–152):

> By default backups live in the `keycloak-database-backups` Docker volume — if the host dies, backups die with it. For disaster recovery, bind-mount the backup path to a host directory…

…and shows a `docker-compose.override.yml` snippet. There is no actual `docker-compose.override.yml.example` file in the repo. Users have to copy the snippet from the README, paste into a new file, and remember to keep the path in sync with `${KEYCLOAK_POSTGRES_BACKUPS_PATH}`.

**Status:** ⚠️ PARTIAL.
**Severity:** MEDIUM.
**Recommendation:** ship `docker-compose.override.yml.example` at repo root. README "Backups" section then points to it: `cp docker-compose.override.yml.example docker-compose.override.yml && $EDITOR …`. Reduces the "I read it but never enabled it" failure mode.
**Effort:** ~30 minutes including README cross-link update.

### Production checklist is text-only, not machine-checkable

README:109–117 has a 7-item checklist that gates production deploys (rotate bootstrap admin, strong secrets, host-mount backups, verify Let's Encrypt, lock down Traefik dashboard, plan upgrade path, know restore procedure). All seven are necessary. None can be automatically verified.

**Status:** ⚠️ PARTIAL.
**Severity:** LOW (nice-to-have, not a security gap by itself).
**Recommendation:** an opt-in `scripts/production-readiness-check.sh` that asserts the checkable items (e.g., `KEYCLOAK_ADMIN_PASSWORD` length ≥ 24 chars, the override file is bind-mounted, the Traefik dashboard hostname has a `IPAllowList` middleware, backup volume is bind-mounted, etc.). Run it once before exposing to users.
**Effort:** ~2 hours — could be deferred to "future work" without blocking anything.

### Pre-rotation advisory placement

SECURITY.md has a "Known historical issue" section explaining the pre-PR-#12 credential commit. README's "Security Notes" repeats it. Both are correct and accurate. Long-term, the README repetition could move into SECURITY.md only — README's Security Notes section then just says "see SECURITY.md → Known historical issue".

**Status:** ⚠️ PARTIAL (cosmetic).
**Severity:** LOW.
**Recommendation:** consider removing the duplicated paragraph from README in a future docs-cleanup PR. Keeps the README's Security Notes evergreen rather than carrying a 2026-04 historical reference forever.
**Effort:** ~10 minutes.

### `KEYCLOAK_BACKUP_INIT_SLEEP=30m` default is excessive

Given the existing `depends_on: postgres: condition: service_healthy` plus the postgres healthcheck's `start_period: 60s`, by the time the backups container starts, postgres is already accepting connections. A 30-minute warm-up means the first backup runs ~31 minutes after `docker compose up -d`. If the deploy fails between minute 1 and minute 31 (e.g., disk fills up), no backup ever runs.

**Status:** ⚠️ PARTIAL.
**Severity:** LOW.
**Recommendation:** lower the default to `60s` (or even `30s`). Document in `.env.example` that the `depends_on: condition: service_healthy` already gates startup. Operators with very large databases on slow disks can still raise it manually.
**Effort:** 5 minutes.

## Findings prioritized by severity

### HIGH

1. **No container security context on any service.** `security_opt: no-new-privileges:true`, `cap_drop: [ALL]`, `read_only: true` all absent. Single-CVE-to-host-compromise blast radius is wider than necessary. _Fix: implement Phase 7 from the proposed runbook._
2. **No resource limits on any service.** A misbehaving Keycloak / Postgres can OOM-kill the host or starve sibling stacks. _Fix: add `deploy.resources.limits.memory` + `cpus` per service per Phase 7._
3. **No semver release tags.** Users have no stable reference point; cannot follow the README's own "pin for production" advice for the deployment template itself. _Fix: tag a release. `v1.0.0` after Phase 7 lands, or `v0.9.0` now if Phase 7 is deferred._

### MEDIUM

1. **`user:` directive missing on every service.** Relies on upstream-image-default user behavior; invisible from compose, fragile to upstream rebase. _Fix: add `user: "<uid>:<gid>"` to each service after confirming the upstream default with `docker run --rm <image> id`._
2. **Off-host backup replication is README-only.** No `docker-compose.override.yml.example` ships in the repo. Increases the "I read it but never enabled it" failure mode. _Fix: ship the override example file._

### LOW

1. **Production checklist is text-only.** Could become a `scripts/production-readiness-check.sh`. Defer.
2. **Pre-rotation advisory is duplicated** between README Security Notes and SECURITY.md. Consider consolidating in a future docs-cleanup PR.
3. **`KEYCLOAK_BACKUP_INIT_SLEEP=30m` default is excessive** given `depends_on: condition: service_healthy`. Reduce to `60s`.
4. **Backup sidecar's missing healthcheck is undocumented.** Add a comment explaining why the sidecar is exempt from the healthcheck pattern.

## Recommended remediation order

### Priority 1 — apply Phase 7 (HIGH severity, ~3–4 h)

Single PR titled `feat(security): container security context + resource limits` per the runbook's Phase 7 commit message template. Steps:

1. Create branch `feat/container-security-context-and-resource-limits`.
2. Add `security_opt: ["no-new-privileges:true"]` to all four services.
3. Add `cap_drop: [ALL]` to all four services. Test:
   - traefik likely needs `cap_add: [NET_BIND_SERVICE]` to bind 80/443 (or use `sysctl net.ipv4.ip_unprivileged_port_start: 0` at host level — out of scope for the compose file).
   - postgres / keycloak / backups likely need nothing.
4. Add `read_only: true` per service plus tmpfs mounts:
   - **postgres:** `tmpfs: [/var/run/postgresql, /tmp]`. Persistent state already on `keycloak-postgres` volume.
   - **keycloak:** `tmpfs: [/tmp, /opt/keycloak/data/tmp]` (verify by inspecting upstream image's runtime writes).
   - **traefik:** `tmpfs: [/tmp]`. ACME storage on volume; docker socket is read-only mount already.
   - **backups:** `tmpfs: [/tmp]`. Backups path on volume.
   Stage one service at a time, watch logs after compose up, add tmpfs paths as `EROFS` errors surface.
5. Add resource limits per service:
   ```yaml
   keycloak:
     deploy: { resources: { limits: { memory: 1g, cpus: "1.5" } } }
   postgres:
     deploy: { resources: { limits: { memory: 512m, cpus: "1" } } }
   traefik:
     deploy: { resources: { limits: { memory: 256m, cpus: "0.5" } } }
   backups:
     deploy: { resources: { limits: { memory: 256m, cpus: "0.25" } } }
   ```
6. Add explicit `user:` per service (pairs naturally with this PR — confirm upstream user, declare it):
   ```bash
   docker run --rm postgres:16 id           # → uid=999(postgres) ...
   docker run --rm quay.io/keycloak/keycloak:26.2.5 id  # → uid=1000(keycloak) ...
   docker run --rm traefik:3.2 id           # → uid=0(root) — leave traefik unset
   ```
7. Add a comment to the `backups` service documenting why no healthcheck (sidecar with infinite loop).
8. Verify locally: full `docker compose up -d`, all services healthy, `docker inspect` confirms each setting.
9. CI's existing `deploy-and-test` job validates the change end-to-end; the existing `backup-restore-e2e` job confirms the backup sidecar still works under read_only.
10. Update CHANGELOG `[Unreleased] → Changed` per the runbook's Phase 7 commit-message template.

### Priority 2 — semver release (HIGH, ~30 min)

After Priority 1 merges:

1. Edit `CHANGELOG.md`: replace `[Unreleased]` heading with `[1.0.0] - 2026-MM-DD`. Re-add an empty `[Unreleased]` above. Update link references at file bottom.
2. `git tag -a v1.0.0 -m "Initial semver release" && git push origin v1.0.0`.
3. GitHub auto-creates release page; optionally edit to copy CHANGELOG `[1.0.0]` body into the release notes.
4. Update README's "Getting started" section to optionally suggest `git checkout v1.0.0` for users who want a stable pin.

### Priority 3 — MEDIUM findings (~2 h, can be one PR or two)

1. Ship `docker-compose.override.yml.example` with bind-mount for the backups path. README "Backups" section updated to point at the file.
2. The `user:` directive is bundled into Priority 1 above (not a separate task).

### Priority 4 — LOW findings (defer or batch)

Leave for a future docs-cleanup PR. None block production users today.

### Estimated total effort to bring fully to standard: ~6 hours

Phase 7 (3.5 h) + semver release (0.5 h) + override file (1 h) + verification + write-up (1 h).

## Recommendations for the runbook itself

The audit surfaced two patterns in this repo that are above the current runbook's standard and should be folded back into the runbook:

1. **`backup-restore-e2e` CI job pattern.** This repo's `deployment-verification.yml` has a fourth job that runs end-to-end backup/restore tests with short backup intervals. The runbook currently has nothing about operational testing beyond the deploy-and-test smoke. Worth a section addendum (Phase 6.5 or under "Optional — operational testing") describing the pattern: separate job parallel to deploy-and-test, `needs: lint`, ephemeral `.env` with short timing knobs, shell-based test cases in `tests/`, `tests/README.md` documenting them.
2. **RTO/RPO documentation table.** The README's Restoring section ships a clean RTO/RPO table with tightening knobs. Worth pulling into the runbook's Phase 4 (README rewrite) as a recommended subsection for stacks with backup capability.

These are not corrections — the existing runbook isn't wrong. They are concrete patterns this reference implementation evolved that the runbook should incorporate so future Type B repos benefit.
